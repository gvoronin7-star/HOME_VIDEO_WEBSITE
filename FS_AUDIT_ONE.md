## 2. АНАЛИЗ РИСКОВ

### 2.1. Технические риски

| Риск | Вероятность | Влияние | Описание |
|------|------------|---------|----------|
| FFmpeg блокирует сервер при рендере | **Высокая** | **Высокое** | `execSync` в `prepareSlides` вызывает FFmpeg синхронно для каждого слайда. При 20 фото сервер не отвечает на запросы ~1-3 мин. |
| Сервер падает при нехватке памяти | Средняя | Высокое | Загрузка 20 фото по 10МБ = 200МБ в памяти (multer memoryStorage). sharp создаёт доп. буферы. |
| OpenAI API недоступен или rate-limited | Средняя | Среднее | Есть fallback на mock, но качество текста падает. Нет retry с экспоненциальной задержкой. |
| Потеря данных при сбое во время генерации | Средняя | Среднее | Нет транзакций БД при обновлении статуса. Сбой между шагами оставляет историю в промежуточном статусе. |
| Конфигурация окружения на демо-машине | Высокая | Высокое | Нет Docker. FFmpeg, Node.js, зависимости — всё настраивается вручную. Риск «работает на моей машине». |
| Переполнение диска временными файлами | Низкая | Среднее | Метод очистки есть, но не запланирован (нет cron). Temp-файлы копятся. |

### 2.2. Функциональные риски

| Риск | Вероятность | Влияние | Описание |
|------|------------|---------|----------|
| Видео без звука на демо | **100%** | **Высокое** | TTS генерирует тишину. Демо «семейного видео с озвучкой» без озвучки — провал. |
| Нет редактирования сценария | Высокая | Среднее | ТЗ описывает сценарий «Опытный» с ручным редактированием. API есть, UI нет. |
| Нет голосового ввода | Высокая | Среднее | Сценарий «Подарок» требует STT. Полностью отсутствует. |
| Нет мини-превью | Средняя | Низкое | Метод есть, не подключён. Для демо можно не показывать. |
| Нет индикатора прогресса рендера | Высокая | Среднее | Polling каждые 3 сек, но прогресс-бар — анимация-pulse без реальных процентов. Пользователь не понимает, сколько ждать. |

### 2.3. Ресурсные риски

| Риск | Вероятность | Влияние | Описание |
|------|------------|---------|----------|
| Дублирование логики контроллер/воркер усложняет доработку | Высокая | Среднее | Любое изменение пайплайна нужно вносить в 2 места. Риск рассинхронизации. |
| Нет тестов — регрессии при доработке | Высокая | Высокое | Любое изменение может сломать существующий функционал без обнаружения. |
| Переход на ASP.NET Core = переписывание с нуля | 100% | **Критическое** | Если следовать ТЗ буквально по стеку, нужно переписать весь backend. ~3-4 недели минимум. |
| Интеграция реального TTS за 2 недели | Средняя | Высокое | Azure Speech / Yandex SpeechKit требуют регистрации, ключей, отладки. Риск задержки. |

### Стратегия В — Полная переработка («Rewrite on ASP.NET Core»)

**Суть:** Переписать backend с нуля на ASP.NET Core 8 + EF Core + Hangfire, как требует ТЗ.

#### Почему текущий стек «не подходит» (аргументы за переработку)

- ТЗ явно указывает ASP.NET Core 8 / C# / EF Core / Hangfire
- Требуется Clean Architecture (Core / Infrastructure / Api / Worker / Tests)
- Команда (предположительно) работает в Visual Studio с C#

#### Почему текущий стек фактически пригоден (контраргументы)

## 4. РЕКОМЕНДУЕМАЯ СТРАТЕГИЯ

### Выбор: Стратегия А (Минимальные изменения) + элементы Стратегии Б

### Обоснование

| Критерий | Стратегия А | Стратегия Б | Стратегия В |
|----------|------------|------------|------------|
| Время | **8 дней** ✅ | 12 дней ⚠️ | 18 дней ❌ |
| Укладывается в 2 недели | **Да** ✅ | На грани ⚠️ | Нет ❌ |
| Риск | **Низкий** ✅ | Средний ⚠️ | Высокий ❌ |
| Качество демо | Достаточное ⚠️ | Хорошее ✅ | Не успеем ❌ |
| Стоимость (человеко-дни) | **8** ✅ | 12 | 18 |
| Использование существующего кода | **Максимальное** ✅ | Высокое | Ноль ❌ |

### Ключевые аргументы

1. **Время — главный фактор.** 2 недели = 10 рабочих дней. Стратегия А (8 дней) оставляет буфер на отладку и непредвиденные проблемы. Стратегия Б (12 дней) — буфер минимален. Стратегия В (18 дней) — нереалистична.

2. **Существующий код работает.** 14 API-эндпоинтов, 7 фронтенд-страниц, 6 сервисов — всё функционирует. Выбрасывать это ради соответствия стеку ТЗ — нерационально.

3. **TTS — единственный реальный блокер.** Браузерный TTS через Web Speech API — рабочее решение для демо. Не требует API-ключей, регистрации, оплаты. Качество ниже профессионального, но для прототипа достаточно.

4. **Docker — обязателен.** Без него демо рискует «не завестись» на чужой машине. Это первый приоритет.

5. **FFmpeg async — простой фикс.** Замена `execSync` → `spawn` — 30 минут работы, но устраняет блокировку сервера.

6. **Несоответствие стека ТЗ — не блокер для демо.** ТЗ допускает React+TypeScript. Backend на Node.js вместо ASP.NET Core — функционально эквивалентен. Вопрос стека можно решить позже.

## 6. ИТОГОВОЕ ЗАКЛЮЧЕНИЕ

### Краткий вывод по состоянию системы

Текущая система — **работающий MVP на 70% готовности**. Архитектура заложена грамотно, 14 API-эндпоинтов и 7 фронтенд-страниц функциональны. Документация выше среднего. Однако три критических пробела делают систему неготовой к демо без доработки:

1. **TTS не реализован** — видео без звука
2. **FFmpeg блокирует сервер** — `execSync` вместо async
3. **Нет Docker** — невозможно быстро развернуть

Очереди задач (BullMQ) и S3-хранилище — значительные пробелы, но **не блокируют демо**. Несоответствие стека ТЗ (Node.js вместо ASP.NET Core) — не блокер, т.к. ТЗ допускает React+TypeScript, а backend-стек функционально эквивалентен.

### Рекомендация по стратегии

**Стратегия А (Минимальные изменения)** — оптимальный баланс времени, риска и качества для 2-недельного спринта. Ключевые действия:

1. Docker (день 1-2) — устраняет риск «не заводится на чужой машине»
2. Браузерный TTS (день 3-5) — устраняет главный функциональный пробел
3. Async FFmpeg (день 1-2) — устраняет блокировку сервера
4. E2E-тесты (день 6-9) — снижают риск регрессий на демо

Перенос на ASP.NET Core (Стратегия В) категорически **не рекомендуется** — не укладывается в сроки и уничтожает работающий код.

### Прогноз по срокам и бюджету

| Параметр | Значение |
|----------|----------|
| Время на базовый план | 8 рабочих дней |
| Время с полировкой и буфером | 10-14 рабочих дней (2 недели) |
